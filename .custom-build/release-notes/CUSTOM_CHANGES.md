### Mihomo：direct proxy 跟随接口 DNS

- direct proxy 支持 `dns-follow-interface`；仅在配置 `interface-name` 时生效，省略默认为 `true`。
- direct proxy 支持 `allow-other-interface`，省略默认为 `true`；指定接口不存在、未运行或缺少目标协议族地址时，连接和接口 DNS 一并回退到当前默认接口。
- 显式设为 `false` 时保持严格接口绑定；接口可用但普通连接失败时不会越权回退。
- macOS 的 `dhcp://<interface>` 优先读取系统 Scoped Resolver，读取不到时再使用 Mihomo DHCP 广播；DNS 失败或连接重置时按需刷新并重试，其他平台保留原一小时缓存。
- 标记位于 `core/Clash.Meta/adapter/outbound/direct.go`、`component/dialer/options.go`、`component/dhcp/dhcp.go` 和 `dns/dhcp.go`；对应目录测试必须保留。

### Tailscale 接入（App 共存：桌面端；内置节点：全平台）

- 网络设置新增「Tailscale 共存」，默认关闭；齿轮入口可自定义排除网段（默认 `100.64.0.0/10`、`fd7a:115c:a1e0::/48`）、MagicDNS 域名（默认 `ts.net`）、MagicDNS 服务器（默认 `100.100.100.100`，留空只返回真实 IP 不改 DNS 服务器）与系统代理例外（默认 `*.ts.net`、`100.64.0.0/10`），右上角一键恢复默认且保留开关状态。

- 内核 TUN `auto-detect-interface` 对落在 `route-exclude-address` 内的目标不再绑定默认网卡，交由系统路由（如 Tailscale utun）；DNS 请求 `100.100.100.100`、系统代理 DIRECT 访问 Tailnet 因此可达。显式配置全局 `interface-name` 时仍以该网卡为准。
- 2026-11-02 Tailscale 服务域名：开启时内核固定把 `tailscaleServiceDomains`（`tailscale.com`、`tailscale.io`，`core/patch_tailscale.go`）加入 fake-ip-filter（blacklist 为 `+.domain`，rule 为 `DOMAIN-SUFFIX,domain,real-ip`），**不加** `nameserver-policy` 与 DIRECT 规则。原因：tsnet（Rex 内嵌节点）与 Tailscale 客户端把连接绑定物理网卡绕过 TUN，拿到 Fake-IP 时 `fetch control key` 黑洞，登录无响应；而 MagicDNS `100.100.100.100` 对非 Tailnet 域名返回 SERVFAIL，交给它会让浏览器打开 `login.tailscale.com` 报 NXDOMAIN，所以不能放进用户的 MagicDNS 域名列表。同时去掉 `core/patch.go` 中重复的 `patchTailscaleDns` 调用。回归为 `core/patch_tailscale_test.go`；实机验证 Rex 设置页 Sign in 可弹出登录页、`lsof` 中 tsnet 连接目标为真实 IP。

### macOS TUN、DNS 与唤醒恢复

- macOS 实际 TUN 配置将 `system` 栈映射为 `mixed`；显式 `mixed` 或 `gvisor` 保持原值。

### 统一启停交互

- 桌面端系统代理或 TUN 任一开启即启动核心，两者均关闭即停止核心；设置页、快捷卡片和托盘开关都调用 `updateSystemProxy` / `updateTun` 联动方法。Windows、macOS 和 Linux 的 TUN 首次启动统一同步执行无 TUN 基线配置、管理员授权、必要的特权核心重启、监听启动和 TUN 配置应用，任一步失败都会停止监听并回滚 TUN 开关；系统代理仍开启时恢复无 TUN 核心，避免 UI 已开启但实际网络黑洞。桌面窗口展示不等待该同步安全链路完成，因此 Windows 开启 TUN 后重启应用仍会先显示窗口，再在后台事件循环中完成授权和网络就绪。
- 首次安装默认关闭系统代理和 TUN；首次添加配置且两个网络开关均关闭时只加载配置，不执行桌面 Core 硬重启，避免配置刚落盘时出现 Core 异常退出。已有配置中显式保存的开关状态保持不变。
- Windows 首次开启 TUN 时只执行一次 Helper 初始状态判断、一次无 TUN 基线配置和一次 TUN 应用；需要提权时仍保留 Helper 健康等待与特权 Core 重启，但不再重复解析配置或二次检查管理员状态。macOS 沿用同一启动顺序且不增加额外工作。
- 桌面 TUN 只有在监听启动、TUN 配置应用和 Core 健康检查全部成功后才进入运行态；普通 Core 进程退出或 Helper Core 的 IPC 控制连接异常断开时，统一关闭系统代理与 TUN 的期望/实际状态，清理运行时和流量展示，更新托盘并立即持久化。初始化失败时主窗口继续可用且两个网络开关保持关闭；用户再次开启网络时会先检测并重启不可用的 Core。
- 系统代理和 TUN 开关在执行配置更新前先用 Core IPC 健康检查校验 `globalState.isStart`；当运行标记存在但 Core 已退出或 IPC 已断时，自动走快速启动恢复链路重建 Core，不再直接向失效 socket 发送 `updateConfig` 导致 `TimeoutException: Core socket connection timed out`。
- 桌面核心实际运行状态统一以 `globalState.isStart` 为准并同步到展示状态；Windows 系统代理调用串行执行，同时写入 WinINet 默认/RAS 连接和当前用户 `Internet Settings` 注册表，任一主通道成功即可完成启停，设置刷新尽力执行，避免特定 Windows 环境拒绝默认连接 API 时无法开启代理。启动配置要求开启系统代理时，初始化阶段延后首次同步，等待核心监听就绪后直接启用，不再先关闭再串行开启；配置要求关闭时仍立即清理残留代理。
- 移除桌面独立启动/停止入口、启动热键和“联动开关”设置；托盘保留网络面板、系统代理、TUN、重启内核等入口。
- Android 首页保留一个悬浮总开关，并避让底部导航与页面滚动内容；启动时间卡片仅作为非独立启停的运行时长展示，不再提供桌面独立启停操作。
